Turing Machine Studio


A browser version of the command-line simulator Turing.py. It reads the same .tm files, compiles them with the same checks (plus a few more), and lets you run, step backwards, edit the tape and change rules while the machine is running, while a live state diagram shows every transition. Rules can carry comments and each machine a “how it works” explanation. Everything is in one HTML file: no install, no server, no internet connection needed.

Quick start


    
  
  1. Open Examples and press Load on any machine, e.g. Add Two Unary Numbers.
    2. 
  
  2. On Run & Debug, press Step (or →) to execute one transition, or Run (Space) to animate.
    3. 
  
  3. Press Back (←) to undo a step. Every step and edit can be undone.
    4. 
  
  4. Edit the text, then press Compile (Ctrl/⌘+Enter).
    5. 
  
  5. Or build a machine without writing text: open Editor, fill in the form, and press Compile & load into engine.
    6. 
  
  6. Save .tm downloads the machine; it runs unchanged with python3 Turing.py file.tm.
    7. 




The five tabs


1 · Run & Debug


    
  
  • Toolbar – Compile, Reset, Send to Editor (opens this machine in the form on the Editor tab, to change it field by field), Rewind to step 0, Back, Step, Run/Pause, To end (full speed), run speed, and Go to step n. The pill on the right shows the status: Not compiled, Ready, Running, Halted, Stuck or Compile errors.
    • 
  
  • Pinned tape – the toolbar and the tape stay at the top of the window while you scroll down to the diagram, rules, log and trace (on short or narrow screens they scroll normally). 📌 Pin tape in the status strip turns this off or on.
    • 
  
  • Arrange the panels – everything under the tape (State diagram, Machine definition, Machine, Transition rules, Execution log, State trace, Diagram at every step) is a panel you can arrange: drag it by its header bar and drop it where you want it — a blue marker shows where it will land: on the top or bottom half of another panel to go above or below it, on its left or right edge to sit side by side with it (both become half width), or below the last panel to go to the end (the page scrolls while you drag near the edges; Esc cancels). You can also use ↑ ↓; ⇔ switches between full and half width (two half panels sit side by side); ▾ or a click on the title collapses it to its header. The Panels bar has Expand all, Collapse all and ⟲ Reset view, which restores the default arrangement. The layout is remembered in the browser.
    • 
  
  • Status strip – current state (a drop-down: change it by hand), step count, head position, the symbol under the head, and how much tape has been used. Save tape → Input writes the current tape and head position back into the editor as Input and Position.
    • 
  
  • Tape – the used part of the tape plus a few blank cells either side (shaded). The orange marker is the head, labelled with the current state. Click a cell to change its symbol. To move the head, drag the orange head marker (or the cell it is on) to any cell — the tape scrolls when you reach its edge, and a running machine pauses first — or double-click a cell. Click the head marker to change the state the head is in. Head moves and state changes are logged and undone with Back.
    • 
  
  • Next – which rule fires next, what it will do and its comment. When the machine stops it shows the result: time (steps), space (tape used), input and output. If no rule applies it offers to add one.
    • 
  
  • State diagram – the rules drawn as states and arrows, highlighting the current state, the step just taken and the next one as you run. See below.
    • 
  
  • Machine definition – the editor with line numbers. Lines with errors are marked in the gutter. New, Open (load a .tm from disk) and Save .tm sit above it.
    • 
  
  • Compiler output – each compile phase with ✓/✗, then every error (✗), warning (!) and note (i). Click one to jump to its line.
    • 
  
  • Machine – everything the compiler understood: name, description, the how it works explanation, alphabet (blank and wildcard labelled), states (start and final labelled, the current one highlighted), shift symbols, input and rule coverage.
    • 
  
  • Transition rules – the rules as an editable table. Change any cell from its drop-down, or type in the Comment column to say what the rule does; the change applies immediately, even while running, and is written back into the editor text. The row that fires next is highlighted; Hits counts how often each rule fired. The dot on the left sets a breakpoint. ✕ deletes a rule; Add rule and Sort are in the header.
    • 
  
  • Execution log – a complete record of compiles, every step (with a tape snapshot and the rule's comment), undos, edits, runs, pauses and the final summary. Filter it, follow it, Download log as text, or Download report (see Execution report).
    • 
  
  • State trace – under the log: the run as a path through the diagram, state after state. See below.

2 · Editor


A one-page form for creating a machine without typing the file format. It opens prefilled with the configured defaults and a small working example (flip every bit), so you can change it rather than start from nothing.


    
  
  • 1 · Machine – name, description and How it works: free text explaining the machine (several lines and paragraphs).
    • 
  
  • 2 · Tape alphabet – one column per symbol; the dashed + tile adds another column, ✕ removes one. Under each symbol choose which one is the blank and which is any (the wildcard). Then the Input and the starting Head position; input characters outside the alphabet are flagged as you type.
    • 
  
  • 3 · States – one column per state, with + to add more. Pick the start state and tick the final states.
    • 
  
  • 4 · Head moves – the words for left, right and stay (default L, R, N).
    • 
  
  • 5 · Transition rules – one row per rule, each cell a drop-down of the states and symbols defined above, plus a free-text Comment saying what the rule is for. + Add rule appends a row; the + at the end of a row inserts one below it; ✕ deletes. Rows with the same State and Read are shaded red.
    • 
  
  • 6 · State diagram – the machine drawn from the form, redrawn as you type. Hover a state or a rule for details.
    • 



Renaming a symbol or state updates every rule that uses it. Removing one leaves a red (removed) in the rules that used it until you pick a replacement.


The right-hand side shows the generated .tm file, updated as you type, and the compiler output. Regenerate (on the file panel) rebuilds the file from the form and clears old compile marks. The toolbar has Download .tm, Compile (also Ctrl/⌘+Enter on this tab), and Compile & load into engine, which puts the machine on Run & Debug ready to run. Compile also warns about anything the original Turing.py cannot read (such as an empty input), so the downloaded file runs in both. Open .tm loads a file from your computer into the form, Load example… fills the form from any of the example machines (so you can change one field by field), and Import from Run & Debug fills it from the machine currently there (the same as Send to Editor on Run & Debug); Reset to defaults starts over. The form is saved in the browser between visits.


Keeping the two tabs in sync. Turn on Keep Run & Debug and the Editor in sync on the Config tab and both tabs always hold the same machine; a green ⇄ In sync label shows on both. A change on the form is applied to Run & Debug about half a second after you stop typing, as soon as it compiles (the run restarts from step 0). A compile, a rule edit in the Transition rules table or Save tape → Input on Run & Debug updates the form. Typing in the Run & Debug text only syncs when you compile, so a half-typed line never replaces the form. While one side has errors the other keeps the last working machine, and the label turns amber to say so. Turning the option on copies the Run & Debug machine into the form.


3 · Config & Defaults


Defaults used when a file leaves a key out (identical to Turing.py), run speed, the safety step limit, logging detail, how many frames the Diagram at every step panel draws, two semantic choices for the wildcard, and editor behaviour. Settings are kept in the browser. Settings that change how machines compile show a Recompile now banner.

The .tm file format


A machine file is plain text. Lines starting with # are comments; blank lines are ignored. Every other line is one of: a setting (Key = Value), the rules header (starting with S.No), or a rule row (starting with a number).



  
KeyMeaningDefault

  
    
NameName shown in the summaryTuring Machine

    
DescriptionFree textTuring machine

    
Tape_AlphabetComma-separated list of every symbol that may be on the tape. One character each.required

    
Blank_SymbolWhat an unwritten cell contains. Must be in the alphabet.#

    
Any_Symbol_Wild_CardIn the Read column, matches any symbol that has no exact rule.?

    
InputInitial tape contents, starting at cell 0.empty

    
PositionInitial head cell (0 = first character). May be beyond the input.0

    
StatesComma-separated list of all states. Names are free-form.required

    
Initial_StateThe start state.required

    
Final_StatesComma-separated list; entering any of them halts the machine.required

    
Left_Shift_Symbol, Right_Shift_Symbol, No_Shift_SymbolThe words used in the Move column.L, R, N

  



Rules follow an optional header line. Each rule row has six comma-separated columns, then an optional seventh column, a free-text comment describing the rule. Spaces and tabs are ignored in the first six columns; the comment keeps its spaces and may contain commas (everything after the sixth comma is the comment):


S.No, Current_State, Input_Alphabet, Output_Alphabet, New_State, Left_Right_No_Shift, Comment
1,    Q0,            0,              x,               Q1,        R,                   Mark the next digit of A as x


Read it as: rule 1 — in state Q0, reading 0, write x, go to Q1, move right. At most one rule may exist per (state, read symbol); that keeps the machine deterministic.



The “how it works” explanation


Lines that start with #> hold the machine's explanation, in plain text. A line with only #> is an empty line between paragraphs. Because they start with #, every Turing.py version treats them as comments.


#> Inverts a binary string: every 0 becomes 1 and every 1 becomes 0.
#>
#> Q0 moves right flipping each bit; at the blank it stops in Q1.


All the example files include an explanation and a comment on every rule.



How a step works


    
  
  1. Read the symbol under the head (a never-written cell reads as the blank).
    2. 
  
  2. Find the rule for (current state, symbol). If none exists, use the state's wildcard rule. If there is neither, the machine is stuck and stops.
    3. 
  
  3. Write the rule's output symbol, change to its new state, and move the head left, right or not at all.
    4. 
  
  4. If the new state is a final state, the machine halts.
    5. 



The tape is unbounded in both directions. "Tape used" (space complexity) is the length of the stretch from the leftmost to the rightmost cell the head has visited, the same measure Turing.py prints. "Steps" is the time complexity.



State diagram and state trace


The diagram is drawn on the fly from the transition rules, on the Editor tab (from the form) and on Run & Debug (from the compiled machine). Each state is a circle — a double ring for final states, with a start arrow into the start state. Each arrow carries one line per rule, #rule-number  read → write, move (for example #1  0 → x, R), in every diagram — Run & Debug, Editor, full screen, the step frames and the downloads; a rule that stays in its state is a loop above the circle. States are laid out left to right by how far they are from the start state, so the diagram roughly follows the order the machine runs in. Actual size / Fit to width switches the zoom.


While the machine runs, the current state is filled orange (green when halted, red when stuck), the arrow of the step just taken is solid orange, and the arrow that fires next is dashed. Hover a state to see every rule leaving it, or a rule line to see what it does and its comment.


The state trace under the log shows the run as a path through the diagram: (Q0) —#0 0→x, R→ (Q1) —#1 0→0, R→ (Q1) …. Each arrow is one step: the symbol read, the symbol written and the move, with the step number above it. Hover a step for the full details (cell, rule, comment) — its arrow lights up blue in the diagram. Click a state to go to that point in the run. Manual edits appear as ✎. The trace follows stepping back, and shows the most recent 400 steps.



Full screen


Click any diagram — on the Editor, on Run & Debug, or one of the frames below — or press ⛶ Full screen to open it filling the window. Zoom with − / + / Fit / 100% or Ctrl + mouse wheel, move around by dragging or scrolling, hover for details, and press Esc or ✕ Close to return. Opened from Run & Debug it keeps following the run: the bar has Back, Step and Run (and ← → Space work), and a caption shows the step, state, symbol under the head, tape and next rule. Opened from the Editor it redraws as the form changes.



Diagram at every step


Under the state trace, Diagram at every step draws the full state diagram once per step, one after another, as it looked at that moment: a dashed orange ring on the state the step came from, the transition it took in orange, and the state it is in afterwards filled (green when halted, red when stuck). Each frame's caption gives the step number, what was read and written, the move, the rule, the tape after the step (head in brackets) and the rule's comment. The first frame is the start; manual edits get a frame of their own. Scanning the frames is a quick way to find the exact moment a complex machine goes wrong.


Choose how many recent frames to show (12, 24, 60, or “all” up to the limit set by Frames shown in “Diagram at every step” on the Config tab, 500 by default) and Large for one frame per row. Download all frames saves one HTML file with every frame of the whole run (never limited by that setting), shown 100 at a time with Previous / Next; it opens in any browser and prints one frame per block.



Execution report (download)


Download report (on the log and the trace) saves one HTML file that opens in any browser, without this app. It contains:


    
  
  • the result: outcome, steps (time), tape used (space), input and final tape;
    • 
  
  • the machine and its how it works explanation;
    • 
  
  • the transition rules with comments and how often each fired;
    • 
  
  • the state diagram with a step player: drag the slider or press Play to watch the run move through the diagram;
    • 
  
  • the diagram at every step (the same frames as above, 100 per page);
    • 
  
  • every step in a table — state, tape (head in brackets), read, write, move, next state, rule and comment — including manual edits (the first 5,000 steps; click a row to show it in the diagram);
    • 
  
  • the complete execution log.
    • 



It reports the run as it is when you download it, so run to the end first for the full story. It also prints well.



Debugging features


    
  
  • Step back undoes exactly one entry: a step, a cell edit, a head move or a state change. Only the change itself is stored, so long runs can be rewound cheaply.
    • 
  
  • Go to step moves backwards (by undoing) or forwards (by executing) to any step number.
    • 
  
  • Breakpoints on rules pause a Run just before that rule fires.
    • 
  
  • Safety limit pauses a Run after a set number of steps (default 100,000), so a machine that never halts cannot freeze the page.
    • 
  
  • Edit on the fly: change tape cells, move the head, switch the state, or edit, add and delete rules at any point. All edits are logged and undoable (rule edits are undone by editing back).
    • 
  
  • Stuck? The Next line offers to add the missing rule for the exact (state, symbol) pair.
    • 




Problem explanations on hover


Wherever a problem is shown, hovering it (or focusing it with the keyboard) opens a tooltip that says what is wrong and how to fix it. Red means an error that stops the machine from compiling or running; amber is a warning; blue is a note.


    
  
  • Run & Debug – marked line numbers in the editor gutter, every message under Compiler output (including failed phases), warning and error lines in the log, red or amber rows in the rules table (duplicate rules, rules that can never fire), the status pill when the machine has errors, is stuck or has halted, the Stuck label under the tape, and the Edited since last compile badge.
    • 
  
  • Editor – symbol and state columns with a problem (empty, too long, duplicated, containing a comma or space), the section notes such as No blank symbol chosen or No final state, the Input, Position, Name, Description and move fields, rule cells that point to something removed, duplicate rule rows, and the marked lines of the generated file after Compile.
    •

Differences from Turing.py


Any file that runs with Turing.py runs here with the same result. These changes fix problems found when reviewing the Python code:


    
  
  • Spaces around commas in lists are allowed (Tape_Alphabet = 0, 1, #).
    • 
  
  • Values may contain =, and = may be used as a tape symbol.
    • 
  
  • An empty Input, or a Position past the end of the input, pads the tape with blanks instead of crashing.
    • 
  
  • If the initial state is already final, the machine halts at step 0 instead of executing one transition.
    • 
  
  • A missing rule stops the machine as stuck with a clear message, rather than raising an exception.
    • 
  
  • A rule row whose comment contains = is still read as a rule (the repository's Turing.py has the same fix).
    • 
  
  • Unknown keys (typos such as Final_State) are reported with a suggestion instead of being silently ignored; missing required keys are reported up front.
    • 
  
  • Indented comments are recognised. All invalid input characters are listed, not just the first.
    • 
  
  • Extra static analysis: unreachable states, rules that start in a final state, states with no rules, and no reachable final state.
    • 
  
  • Stepping back to step 0 works, and history stores only the changes (not a deep copy of the machine on every step).
    • 



Comments and explanations in Turing.py. The repository's Turing.py has been updated to read the comment column (it shows it with each step) and to print the #> explanation in its summary. An older copy of Turing.py would reject rule rows that have a comment column; explanations are safe everywhere.


Two behaviours are configurable on the Config tab and default to Turing.py's: the wildcard must be in Tape_Alphabet, and a wildcard in the Write column writes the wildcard character itself.



Code structure


The file has three scripts, each commented in detail:


    
  
  • <script id="engine"> – the engine, exposed as the global TM. It has no DOM access. TM.compile(text, cfg) runs the phases read → strip → parse → validate → build and returns the machine plus all diagnostics. TM.createSim, TM.step and TM.undo run it; editCell, moveHead and setState make undoable edits.
    • 
  
  • <script id="examples"> – the example .tm files as text.
    • 
  
  • <script id="ui"> – the interface, in lettered sections A–Q: helpers, configuration, state, log, editor, compile, execution, tape, rules table, rendering, examples, start-up (L), the form-based Editor tab (M), which keeps a small model of the machine and generates the .tm text from it, hover tooltips (N), the state diagram (O: a dependency-free layered layout drawn as SVG, highlighted by toggling CSS classes), the state trace (P), the execution report (Q: replays the run from the history and writes a standalone HTML file), the diagram at every step (R: one base SVG copied per frame; the renderer is self-contained so the downloads embed the same code), and the full-screen viewer (S). Changes call scheduleRender(), which repaints at most once per animation frame.
    • 



To add a built-in example, add an entry {file: "name.tm", text: "…"} to the EXAMPLES array.



Troubleshooting


    
  
  • "Edited since last compile" – the text differs from what is running. Press Compile to apply it. Editing rules in the table does not trigger this; those edits are applied to both.
    • 
  
  • Run is disabled – the machine has halted or is stuck. Press Reset, step back, or fix the tape or rules.
    • 
  
  • Run paused on its own – a breakpoint fired or the safety limit was reached; the log says which.
    • 
  
  • Settings or last machine not remembered – the browser is blocking local storage (e.g. a private window). Everything else works.
    • 




  







  
  

    
About Turing Machine Studio

    
Turing Machine Studio is a free Turing machine simulator that runs entirely in your browser, with nothing to install. A Turing machine is the simplest model of a computer: a tape of symbols, a head that reads and writes one cell at a time, and a table of rules. Alan Turing described it in 1936, and it is still how computer science defines what can be computed.

    
Write a machine as a text file or on a form, compile it, then run it, step forward and back, jump to any step, edit the tape, move the head and change rules while it runs. A live state diagram highlights every transition; the execution log, the state trace and a diagram for every step show exactly what happened. Problems are explained in plain language, and a whole run can be downloaded as an HTML report. It reads and writes the same .tm files as the command-line simulator Turing.py.

    
Useful for learning and teaching the theory of computation, automata and computability, and for exploring famous machines such as the busy beavers.
